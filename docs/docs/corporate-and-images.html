Core concepts

Corporate networks & images

Three opt-in features for real-world networks and image workflows: trust a corporate CA for image pulls, keep pulled images across cluster deletes with a shared registry cache, and run linux/amd64 images through Rosetta. All are off by default and work on kubeadm and k3s clusters on the apple/container backend.

Corporate CAs and TLS-intercepting proxies

Behind Zscaler-style TLS inspection, or when pulling from an internal Nexus or Artifactory with a private CA, node image pulls fail with x509: certificate signed by unknown authority. Give every node your CA:

kiac create cluster --ca-cert ~/corp-root.pem
kiac create cluster --ca-cert ~/corp-root.pem --ca-cert ~/proxy-intercept.pem   # repeatable

Or in a config file: caCerts: [/Users/me/corp-root.pem]. Each file may hold several PEM certificates; anything that is not a certificate (a key, a comment) is ignored, and a file with no valid certificate is rejected before any VM boots.

  • kubeadm nodes install the certificates under /usr/local/share/ca-certificates/kiac/, run update-ca-certificates, and restart containerd before kubeadm init, so every Kubernetes image pull already trusts them.
  • k3s nodes add them to /etc/ssl/certs/ca-certificates.crt in the boot preamble before k3s starts, rebuilding from a pristine copy on every boot so restarts never duplicate entries.
The node image itself. The first pull, of the kindest/node or rancher/k3s image, is made by the host container service, which trusts the macOS System keychain rather than --ca-cert. Corporate-managed Macs usually already have the CA there; if not: sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ~/corp-root.pem, then container system stop && container system start.

--ca-cert is not yet supported on real GPU (krunkit) clusters. If your network also needs an explicit HTTP proxy rather than transparent interception, that is not configured by kiac yet.

A registry cache that outlives your clusters

Deleting a cluster deletes its nodes, and with them every image they pulled; the next cluster downloads them all again. --registry-cache routes pulls through one shared zot pull-through cache instead:

kiac create cluster --registry-cache --workers 2   # starts the cache on first use
kiac delete cluster
kiac create cluster --registry-cache --workers 2   # pulls come from the cache on local disk

Config file: registryCache: true. The cache proxies docker.io, registry.k8s.io, ghcr.io and quay.io, which covers Kubernetes, the built-in addons, and most workloads; images from other registries are pulled directly, as before.

PieceWhere
Cache containerkiac.registry-cache, deliberately outside the kiac-<cluster>- names, so cluster commands never list or delete it
Cached imagesnamed volume kiac.registry-cache; survives deleting clusters and the cache container
Config and upstream CAs~/.kiac/registry-cache/
Node wiringkubeadm: containerd /etc/containerd/certs.d/<registry>/hosts.toml; k3s: /etc/rancher/k3s/registries.yaml; both resolve kiac.registry-cache through /etc/hosts

Manage it with kiac cache:

kiac cache status
kiac cache start                            # start it, re-point running clusters at its address
kiac cache start --ca-cert ~/corp-root.pem  # trust a corporate CA for upstream pulls (restarts the cache)
kiac cache delete                           # remove the container, keep the images
kiac cache delete --purge                   # remove the images too

Resilience. Container addresses change across restarts, so nodes reach the cache by name, and kiac cache start, kiac resume cluster and kiac start node re-point that name. If the cache is stopped or unreachable, containerd and k3s fall back to the upstream registry: the cluster keeps working, just without the cache. --ca-cert given at create also applies to the cache's own upstream pulls.

Trust boundary. The cache is a local development convenience. It listens without authentication on the VM network shared by every cluster, so anything running there can read from it or push to it. Images you load with kiac load image go straight into the nodes and are not kept in the cache.

amd64 images through Rosetta

Nodes are arm64. An image published only for linux/amd64 fails with exec format error. --rosetta starts every node VM with Rosetta registered for x86-64 binaries, inside the node and inside its pods:

kiac create cluster --rosetta

Config file: rosetta: true. Rosetta must be installed on the Mac (softwareupdate --install-rosetta --agree-to-license); the VM refuses to start otherwise. Not available on real GPU clusters.

For amd64 images you build yourself, load the amd64 variant explicitly; without --platform only the node's own arm64 content is imported:

container build --platform linux/amd64 -t legacy:dev .
kiac load image legacy:dev --platform linux/amd64

Pulling amd64-only images from a registry. containerd in the node pulls the node's own platform, so an image with no arm64 variant can still be refused with no match for platform in manifest even with Rosetta on. Pull or build it on the Mac and use kiac load image --platform linux/amd64 instead.

Performance. Prefer native arm64 or multi-arch images whenever they exist. Rosetta for Linux translates each new process from scratch, since its translation cache is not enabled by Apple's container framework yet, so start-up-heavy amd64 workloads are noticeably slower. Treat Rosetta as a compatibility mode, give amd64-heavy nodes more CPUs (for example --cpus 6 or 8 on an M4 Pro), and expect occasional upstream Rosetta bugs.

All together

kiac create cluster --name work --workers 2 \
  --ca-cert ~/corp-root.pem --registry-cache --rosetta

Or in a config file:

name: work
workers: 2
caCerts:
  - /Users/me/corp-root.pem
registryCache: true
rosetta: true
